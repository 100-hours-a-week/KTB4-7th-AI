# 솔루션 축 점수의 변별력 (2026-10-26 실험)

`app/services/solution_focus.py` 가 카드 3장의 근거 지표를 고를 때 쓰는 점수식을 POS
실데이터로 돌려, **점수가 날마다 변하는가**(변별력)와 **어느 축이 실제로 뽑히는가**
(선택률)를 본 실험이다.

점수 기준은 처음부터 잠정값이라고 적어 뒀다(`solution_focus.py` 모듈 독스트링:
*"점수 기준은 잠정값이다 … 효과를 측정해 보려고 합리적인 초안을 넣어 둔 것"*).
근거가 붙은 건 날씨 축 하나뿐이었다([2026-09-08 실험](2026-09-08-weather-sales.md)).

**데이터**: `매출리포트_샘플_260720-261019.xlsx`(토스 POS 상품 주문 상세내역),
18,253행, 2026-07-20 ~ 2026-10-19, **매장 1곳 92일**.
**방법**: 날짜 D 마다 직전 7일을 현재 기간, 그 앞 7일을 이전 기간으로 두고 BE 가 보낼
`metrics` 를 만든 뒤, `solution_focus` 의 점수 함수를 **그대로 불러** 점수를 냈다.
`predictedSalesToday`(예측)·`weatherContext`(날씨)는 POS 에 없어 제외했다 — 따라서
아래 선택률은 4 개 축(시간대·카테고리·매출총액·메뉴) 사이의 경쟁이다.

## 1. 네 축 중 셋이 사실상 상수다

표본 78일, 영업시간 09:00~24:00 고정.

```
축          평균     표준편차   1.0 포화   선택률
시간대      0.983    0.012       0%      100%
카테고리    0.994    0.037      96%      100%
메뉴        1.000    0.000     100%      100%
매출총액    0.324    0.199       0%        0%
```

**메뉴 축은 92일 전부 정확히 1.000 이다.** 표준편차가 0 이다. 카테고리는 96% 의 날에
1.0 으로 포화된다. 시간대는 포화까진 안 가도 0.980~0.999 사이에서만 움직인다.

점수의 목적은 "오늘 이 지표가 특이한가" 를 재는 것인데, 세 축은 날짜와 무관하게 거의
같은 값을 낸다. **특이함을 재는 게 아니라 구조적인 상수를 재고 있다.**

## 2. 유일하게 변별력이 있는 축이 한 번도 안 뽑힌다

매출총액만 분포가 넓다(0.001~0.819, 표준편차 0.199). 그런데 **92일 중 선택 0회**다.
다른 세 축이 늘 0.98 이상이라 0.3 대 점수로는 이길 수가 없다.

결과적으로 카드 3장은 **항상 시간대·카테고리·메뉴**다. `assign()` 의 설계 의도
("오늘 할 말이 있는 것만 고른다")가 선택으로 작동하지 않고 고정 배정이 된다.

28일 창으로 바꿔도 같다(표본 36일): 시간대 0.999·카테고리 0.970·메뉴 1.000·매출총액
0.150, 매출총액 선택률 0%.

## 3. 메뉴 축이 포화되는 이유 — 꼬리 메뉴

`_menu_score` 는 `min(max(|vsPrevPeriod|) × 2.0, 1.0)` 이다. 변화율 **최댓값** 하나로
점수가 정해진다.

마지막 7일 창에 메뉴가 **135종** 있고, 그중 **42종**이 전주 대비 ±50% 이상 움직였다.
변화 1위는 `바닐라아이스크림 (포장불가) +500.0%` — 매출 45,000원, **6개** 팔린 메뉴다.
0.5 × 2.0 = 1.0 이라 이런 메뉴 **한 종만 있어도 점수가 포화된다**. 28일 창은 169종 중
57종이 ±50% 이상이었다.

메뉴가 많은 매장에서는 "최댓값 하나" 가 사실상 항상 상한에 닿는다.

## 4. 대안 두 가지를 같은 데이터로 재봤다

### (a) 변화율 대신 변화 금액 — 전체 매출 대비

```python
min(max(|변화금액|) / 전체매출 × 2.0, 1.0)
```

```
평균 0.057 · 표준편차 0.035 · 1.0 포화 0%
```

포화가 사라진다. 6개 팔린 메뉴는 금액이 작아 점수를 못 올린다. 다만 카드 구성이
뒤집힌다 — 메뉴 축이 거의 안 나오고 매출총액이 대신 들어온다(§6 에 적용 후 실측).

전체 매출을 인자로 더 받지 않아도 된다. `ratio`(현재 비중)와 `vsPrevPeriod` 만으로
**근사가 아니라 정확히 같은 값**이 나온다:

```
변화금액/전체 = (현재 - 이전)/전체
              = (현재/전체) x (현재 - 이전)/현재
              = ratio x vsPrevPeriod/(1 + vsPrevPeriod)
```

### (b) 비중 하한 — 비중 1% 이상 메뉴만 후보

```
평균 0.998 · 표준편차 0.019 · 1.0 포화 99%
```

**효과가 없다.** 비중 1% 이상인 메뉴도 충분히 많아서 그중 하나는 늘 ±50% 움직인다.
꼬리를 자르는 방향으로는 안 풀린다.

### (c) 백분위 변환 — 각 축의 과거 분포 대비 오늘 순위

네 축 전부를 "그 축의 과거 분포에서 오늘이 몇 번째인가" 로 바꿨다(표본 68일,
앞 10일은 분포를 만드느라 제외).

```
시간대 100% · 카테고리 100% · 매출총액 100% · 메뉴 0%
```

매출총액이 들어온다. 대신 메뉴가 0% 가 된다 — 메뉴 점수가 늘 정확히 1.000 이라
"과거보다 큰 날" 이 하루도 없어 백분위가 0 이 된다. **동점 처리를 안 한 결과이고,
포화된 축을 백분위로 바꾸면 이렇게 역전된다**는 점까지가 이 측정이 말할 수 있는
전부다. 포화를 먼저 없애지 않으면 백분위 변환만으로는 안 된다.

## 5. 따로 발견한 것 — 계약이 자정 넘는 영업시간을 표현할 수 없다

이 매장은 **09시 ~ 새벽 2시** 영업이다. 시간대별 매출 비중:

```
21시 10.6%   20시 9.3%   22시 9.7%   15시 8.6%   ...
 0시  3.9%    1시 1.9%    2시 0.4%
 3~8시 0.0~0.1% (매출 있는 날이 92일 중 2~20일)
```

`BusinessHours` 는 `opensAt`/`closesAt` 뿐이고 `_open_hours` 는 `opens <= hour < closes`
로 거른다. 09:00~03:00 을 그대로 보내면:

```
09:00~24:00 (자정에서 끊기)     남는 행 15개 · 시간대 점수  0.912
09:00~03:00 (자정 넘김)         남는 행  0개 · 시간대 점수 -1.000  ← 축 탈락
00:00~24:00 (필터 없음)         남는 행 24개 · 시간대 점수  0.999
```

`9 <= hour < 3` 은 어떤 시간에도 참이 아니라 **행이 전부 걸러지고 시간대 축이 후보에서
탈락한다** — 카드가 한 장 줄어든다. 심야 영업 매장에서 실제로 일어난다. BE 가 지금 어떤
값을 보내는지 확인이 필요하다.

## 6. 적용 — (a) 변화 금액으로 바꿨다 (2026-10-26)

`_menu_score` 를 변화율 최댓값에서 변화 금액(전체 매출 대비)으로 바꾸고, `_menu_rows` 도
같은 기준으로 정렬하게 고쳤다 — 독스트링에 적힌 대로 점수와 보여주는 행의 기준이
어긋나면 "점수를 만든 메뉴가 행에서 빠진다".

같은 POS 데이터를 **배포될 코드로** 다시 돌린 결과(표본 78일, 영업시간 09:00~24:00):

```
축          평균     표준편차   1.0 포화   선택률       (바꾸기 전)
시간대      0.983    0.012       0%      100%      100%
카테고리    0.994    0.037      96%      100%      100%
```

**매출총액 축이 0% → 97% 로 들어왔다.** 92일 내내 한 번도 안 나오던 축이다. 메뉴는

부수 효과: `test_축이_다섯이면_날씨가_밀린다` 가 깨졌다. 그 테스트는 *"축이 다섯이
되면서 날씨 자리가 사실상 사라졌다, 이 테스트가 깨지면 그 결정이 내려진 것"* 이라고
적어 둔 tripwire 였다. 날씨를 건드려서가 아니라 **메뉴 포화가 날씨의 0.3 을 늘 누르고
있었기** 때문이다. 포화를 없애니 날씨 보충 자리가 돌아왔다.

**아직 안 한 것**: 시간대(평균 0.983)·카테고리(96% 포화)의 포화는 그대로다. 카드 품질

### 문제

`_weather_score` 가 `isNotable` 만 보고 **0.3 고정값**을 줬다. 매장 2 곳 639 일에서
매출총액 축이 평균 0.240 이라, 0.3 이 **3 번 자리를 65~69% 차지했다.**

```
평소 날씨(isNotable=true, 0.3) 켰을 때
  카드3: 날씨 69% / 매출총액 31%   (매장A)
         날씨 65% / 매출총액 35%   (매장B)
  → 메뉴 축은 0%
```

"다른 축이 할 말 없을 때만 보충" 이라고 설계했는데 반대로 동작했다. 그리고 기온 구간을
갈라 보면 그 0.3 을 받는 날의 대부분이 **음료 구성이 하루 내내 같은 평범한 날**이었다:

```
구간                                   일수   비율   아이스비중 변동폭(실험 기울기)
① 기상청 특보급 (>=33 또는 <=-12)         36    6%   —
② 하루 안에서 18℃를 가로지름             159   26%   평균 3.7%p (최대 9.8%p)
③ 하루 전부 18℃ 미만 (평범한 겨울)        254   41%   —
④ 하루 전부 18℃ 이상 (포화 구간)         166   27%   —
```

③+④ = **68%** 다. 이 날들도 똑같이 0.3 을 받았다.

### 바꾼 것

[2026-09-08 실험](2026-09-08-weather-sales.md) §1 의 두 실측값을 점수식에 직접 넣었다 —
자릿수 맞추는 임의 가중치를 쓰지 않는다.

```python
if maxTempC >= 33 or minTempC <= -12:          return 1.0    # 기상청 주의보 기준
if not (minTempC < 18 <= maxTempC):            return -1.0   # 구성이 안 갈린다 → 탈락
swing = (18 - max(minTempC, -10)) * 0.0061                   # 1도당 아이스 비중 +0.61%p
return min(swing / 0.14, 1.0)                                # 0.14 = 실험 관측 전체 변동폭
```

- **18℃** = 아이스 비중 포화점 (실험 §1)
- **0.0061** = 18℃ 미만 구간 기울기, 기온 1 도당 +0.61%p (실험 §1)
- **0.14** = 실험이 관측한 전체 변동폭 (0.338 ~ 0.478)
- **−10℃** 아래로는 기울기를 외삽하지 않는다 — 실험의 최저 구간이 (−10, 5] 다
- `isNotable` 게이트는 유지했다 — "BE 판정이 우선, 우리가 덮어쓰지 않는다"(기존 결정)

하루 최저~최고가 포화점을 가로지르는 날은 오전·오후 음료 구성이 갈려서 "오전엔 핫,
오후엔 아이스를 준비하세요" 같은 실행 가능한 말이 나온다. 가로지르지 않으면 하루 내내
같아 할 말이 없다.

### 적용 후 실측 (기상청 기온 × 매장 날짜, `isNotable=true` 가정 = **상한**)

```
매장A (309일)  날씨 발동 27% · 발동 시 평균 0.405 / 최대 1.000 · 카드 선택률 16%
  카드1: 카테고리 76% · 시간대 23% · 날씨 1%
  카드2: 시간대 73% · 카테고리 23% · 날씨 4%
  카드3: 매출총액 76% · 날씨 11% · 메뉴 8% · 시간대 4% · 카테고리 1%

매장B (253일)  날씨 발동 32% · 발동 시 평균 0.408 / 최대 1.000 · 카드 선택률 19%
  카드1: 카테고리 90% · 시간대 9% · 날씨 0%
  카드2: 시간대 85% · 카테고리 9% · 날씨 6%
  카드3: 매출총액 69% · 날씨 13% · 메뉴 11% · 시간대 6% · 카테고리 0%
```

**날씨 선택률 65~69% → 16~19%.** 평범한 날 68% 는 아예 발동하지 않는다. 특보급(한파·폭염)은
1.0 이라 그대로 1~2 번 자리를 얻는다.

### 한계

- **`isNotable=true` 를 전체 날짜에 가정한 상한이다.** 실제로 며칠이 notable 인지는 BE
  판정이라 모른다 — 그만큼 선택률은 더 낮아진다.
- **기상청 서울경기 지역 평균**을 썼다. BE 가 보내는 건 매장 지역 단기예보라 값이 다르다.
- 기온-아이스 비중 관계는 **매장 1 곳 267 일**에서 나온 상관이다. 인과가 아니고
  계절 교란을 못 뺐다([2026-09-08 실험](2026-09-08-weather-sales.md) 한계 절).
- **강수는 여전히 점수에 안 들어간다.** 비 오는 날 매출 −10% 를 쟀지만(실험 §3, 42일)
  `conditionPatterns` 가 이미 강수별 메뉴 패턴을 보내오는데 점수식에 연결돼 있지 않다
  (이슈 #194). 태풍·대설은 풍속·적설이 계약에 없어 판정 못 한다 — PR #227.
- 카드 품질(`공허한_조언`·`수치_정확`)은 GPU 가 꺼져 있어 못 쟀다.

## 9. 시간대·카테고리 포화를 고쳤다 (2026-10-27)

§6~8 로 메뉴·날씨 축은 풀렸지만 **카드 1·2 는 여전히 시간대·카테고리로 고정**이었다
(§7: 시간대 표준편차 0.010~0.022, 카테고리 포화 77~91%). 그 둘을 고친 기록이다.

### 어디서 포화가 나오는지 먼저 갈랐다

카테고리 점수는 `max(비중 최댓값, 증감률 최댓값 x 2.0)` 이다. 두 항을 따로 재봤다
(매장 2 곳, 창 7 일):

```
항                     평균     표준편차   1.0 포화
비중 최댓값             0.358    0.018       0%     ← 상수. 변별이 아니라 하한을 깔고 있었다
현행(두 항의 max)        0.941    0.139      77%     ← 포화는 전부 증감항에서 나온다
```

증감항이 원인이고, 원인은 **§3 의 꼬리 항목 문제와 같다** — 카테고리가 9~17 종이라
비중 1% 짜리 하나가 +400% 움직이면 `0.5 x 2.0` 으로 상한에 닿는다.

### 후보 네 개를 같은 데이터로 재봤다

```
시간대 후보              평균     표준편차    최소     최대   1.0포화
현행 1 - 최저/최고        0.968    0.017    0.890   0.993     0%
유휴 비중                0.246    0.033    0.185   0.318     0%
정규화 HHI              0.027    0.006    0.016   0.041     0%
1 - 중위/최고            0.598    0.081    0.374   0.768     0%

카테고리 후보            평균     표준편차    최소     최대   1.0포화
현행 max(비중, 증감x2)    0.941    0.139    0.346   1.000    77%
변화 금액 최댓값 x2       0.075    0.035    0.023   0.242     0%
비중 총변동거리(TVD)      0.055    0.016    0.021   0.108     0%
비중만                  0.358    0.018    0.311   0.412     0%
```

### 카테고리에 메뉴와 같은 잣대를 쓰면 안 된다

§6 에서 메뉴를 "변화 금액" 으로 바꿨으니 카테고리도 같게 하는 게 자연스러워 보인다.
**아니다.** 카테고리의 변화 금액은 그 카테고리에 속한 메뉴들의 변화 금액 **합**이라
개별 메뉴 최댓값보다 구조적으로 크다. 실제로 그렇게 하면 메뉴 축이 다시 밀린다:

```
카드3 구성          카테고리=TVD        카테고리=변화금액x2
매장A   메뉴            28%                  13%
매장B   메뉴            24%                  12%
```

`_menu_score` 독스트링의 *"메뉴 비중은 카테고리보다 구조적으로 작다 — 같은 잣대로 재면
메뉴 축이 거의 항상 진다"* 와 **반대 방향인 같은 함정**이다. 그래서 잣대를 가른다:
메뉴는 "한 메뉴가 크게 움직였다"(변화 금액 최댓값), 카테고리는 "구성이 재편됐다"(총변동).

### 바꾼 것

```python
# 시간대 — 균등하게 팔렸다면 영업시간 n 개가 1/n 씩 가져간다. 모자란 몫의 합.
#          dayType 별로 따로 재서 더 쏠린 쪽을 쓴다(평일·주말은 다른 계열이다).
even = 1.0 / len(amounts)
score = sum(max(0.0, even - a / total) for a in amounts)

# 카테고리 — 비중의 총변동거리. share 와 vsPrevPeriod 로 이전 비중이 복원된다.
prev_i = share_i / (1 + vsPrevPeriod_i)          # 합으로 나눠 비중으로 되돌린다
score  = 0.5 * sum(|share_i - prev_i_정규화|)
```

둘 다 **자릿수 맞추는 가중치가 없다.** 0~1 범위가 식 자체에서 보장되고, 메뉴·매출총액과
같은 단위(전체 매출 또는 비중의 몇 %)가 된다. 비중 쏠림 항은 뺐다 — "커피가 62%" 는
늘 그래서 뉴스가 아니다(`_menu_score` 의 "늘 아메리카노가 1 위다" 와 같은 판단).

`_category_rows` 도 같이 바꿨다. 점수 기준이 구성 변동으로 바뀌었는데 행은 비중 상위로
고르고 있어서, **가장 많이 움직인 카테고리가 행에 없는 날이 23~29%** 였다(매장A 79/351,
매장B 73/253). §6 에서 `_menu_rows` 로 먼저 겪은 문제다.

### 성립하지 않는 것 — 시간대 축의 날짜별 변별력은 여전히 없다

시간대 표준편차가 0.017 → 0.033 으로 두 배가 됐지만 **여전히 작다.** 그리고 선택률이
639 일 전부 100% 다 — 슬롯은 안 고정됐지만 축 자체는 늘 든다.

이건 점수식으로 풀 수 있는 문제가 아니다. **7 일 창이 하루씩 미끄러지면 6/7 이 겹쳐서
시간대 모양 자체가 거의 안 변한다.** 그리고 `HourlyPoint` 는 `dayType`·`hour`·`amount`
뿐이라 **이전 기간 값이 없다** — 단일 창으로 "오늘 특이한가" 를 재는 건 원리적으로 안 된다.
매출총액 축이 표준편차 0.182 인 건 그 축만 두 기간의 비(`vsPrevPeriod`)이기 때문이다.

이번 변경이 고친 것은 변별력이 아니라 **다른 축을 덮던 높이**다(0.968 → 0.246).
날짜별 변별력까지 가려면 `hourlyProfile` 에 이전 기간 값이 필요하고, 그건 계약 변경이라
BE 협의 사항이다.

- 여전히 **매장 2 곳**이다. 유휴 비중 평균이 두 매장에서 0.246·0.249 로 거의 같은데,

- 날씨는 `isNotable=true` 를 전체 날짜에 가정한 **상한**이다(§8 과 같은 한계).
- **카드 품질은 아직 못 쟀다.** `공허한_조언`·`수치_정확` 은 GPU 가 필요하다. 축 구성이
  바뀌면 품질도 바뀔 수 있다 — 특히 카드 1 이 카테고리에서 시간대로 옮겨갔다.

  실매장 639 일에는 0 건이지만(§7), 분류를 안 한 신규 매장은 카드가 한 장 줄어든다.
