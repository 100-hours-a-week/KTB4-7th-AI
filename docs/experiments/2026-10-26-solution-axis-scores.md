# 솔루션 축 점수의 변별력 (2026-10-26 실험)

`app/services/solution_focus.py` 가 카드 3장의 근거 지표를 고를 때 쓰는 점수식을 POS
실데이터로 돌려, **점수가 날마다 변하는가**(변별력)와 **어느 축이 실제로 뽑히는가**
(선택률)를 본 실험이다.

점수 기준은 처음부터 잠정값이라고 적어 뒀다(`solution_focus.py` 모듈 독스트링:
*"점수 기준은 잠정값이다 … 효과를 측정해 보려고 합리적인 초안을 넣어 둔 것"*).
근거가 붙은 건 날씨 축 하나뿐이었다([2026-09-08 실험](2026-09-08-weather-sales.md)).

**데이터**: `매출리포트_샘플_260720-261019.xlsx`(토스 POS 상품 주문 상세내역),
18,253행, 2026-07-20 ~ 2026-10-19, **매장 1곳 92일**.
**방법**: 날짜 D 마다 직전 7일을 현재 기간, 그 앞 7일을 이전 기간으로 두고 BE 가 보낼
`metrics` 를 만든 뒤, `solution_focus` 의 점수 함수를 **그대로 불러** 점수를 냈다.
`predictedSalesToday`(예측)·`weatherContext`(날씨)는 POS 에 없어 제외했다 — 따라서
아래 선택률은 4 개 축(시간대·카테고리·매출총액·메뉴) 사이의 경쟁이다.

## 1. 네 축 중 셋이 사실상 상수다

표본 78일, 영업시간 09:00~24:00 고정.

```
축          평균     표준편차   1.0 포화   선택률
시간대      0.983    0.012       0%      100%
카테고리    0.994    0.037      96%      100%
메뉴        1.000    0.000     100%      100%
매출총액    0.324    0.199       0%        0%
```

**메뉴 축은 92일 전부 정확히 1.000 이다.** 표준편차가 0 이다. 카테고리는 96% 의 날에
1.0 으로 포화된다. 시간대는 포화까진 안 가도 0.980~0.999 사이에서만 움직인다.

점수의 목적은 "오늘 이 지표가 특이한가" 를 재는 것인데, 세 축은 날짜와 무관하게 거의
같은 값을 낸다. **특이함을 재는 게 아니라 구조적인 상수를 재고 있다.**

## 2. 유일하게 변별력이 있는 축이 한 번도 안 뽑힌다

매출총액만 분포가 넓다(0.001~0.819, 표준편차 0.199). 그런데 **92일 중 선택 0회**다.
다른 세 축이 늘 0.98 이상이라 0.3 대 점수로는 이길 수가 없다.

결과적으로 카드 3장은 **항상 시간대·카테고리·메뉴**다. `assign()` 의 설계 의도
("오늘 할 말이 있는 것만 고른다")가 선택으로 작동하지 않고 고정 배정이 된다.

28일 창으로 바꿔도 같다(표본 36일): 시간대 0.999·카테고리 0.970·메뉴 1.000·매출총액
0.150, 매출총액 선택률 0%.

## 3. 메뉴 축이 포화되는 이유 — 꼬리 메뉴

`_menu_score` 는 `min(max(|vsPrevPeriod|) × 2.0, 1.0)` 이다. 변화율 **최댓값** 하나로
점수가 정해진다.

마지막 7일 창에 메뉴가 **135종** 있고, 그중 **42종**이 전주 대비 ±50% 이상 움직였다.
변화 1위는 `바닐라아이스크림 (포장불가) +500.0%` — 매출 45,000원, **6개** 팔린 메뉴다.
0.5 × 2.0 = 1.0 이라 이런 메뉴 **한 종만 있어도 점수가 포화된다**. 28일 창은 169종 중
57종이 ±50% 이상이었다.

메뉴가 많은 매장에서는 "최댓값 하나" 가 사실상 항상 상한에 닿는다.

## 4. 대안 두 가지를 같은 데이터로 재봤다

### (a) 변화율 대신 변화 금액 — 전체 매출 대비

```python
min(max(|변화금액|) / 전체매출 × 2.0, 1.0)
```

```
평균 0.057 · 표준편차 0.035 · 1.0 포화 0%
```

포화가 사라진다. 6개 팔린 메뉴는 금액이 작아 점수를 못 올린다. 다만 카드 구성이
뒤집힌다 — 메뉴 축이 거의 안 나오고 매출총액이 대신 들어온다(§6 에 적용 후 실측).

전체 매출을 인자로 더 받지 않아도 된다. `ratio`(현재 비중)와 `vsPrevPeriod` 만으로
**근사가 아니라 정확히 같은 값**이 나온다:

```
변화금액/전체 = (현재 - 이전)/전체
              = (현재/전체) x (현재 - 이전)/현재
              = ratio x vsPrevPeriod/(1 + vsPrevPeriod)
```

### (b) 비중 하한 — 비중 1% 이상 메뉴만 후보

```
평균 0.998 · 표준편차 0.019 · 1.0 포화 99%
```

**효과가 없다.** 비중 1% 이상인 메뉴도 충분히 많아서 그중 하나는 늘 ±50% 움직인다.
꼬리를 자르는 방향으로는 안 풀린다.

### (c) 백분위 변환 — 각 축의 과거 분포 대비 오늘 순위

네 축 전부를 "그 축의 과거 분포에서 오늘이 몇 번째인가" 로 바꿨다(표본 68일,
앞 10일은 분포를 만드느라 제외).

```
시간대 100% · 카테고리 100% · 매출총액 100% · 메뉴 0%
```

매출총액이 들어온다. 대신 메뉴가 0% 가 된다 — 메뉴 점수가 늘 정확히 1.000 이라
"과거보다 큰 날" 이 하루도 없어 백분위가 0 이 된다. **동점 처리를 안 한 결과이고,
포화된 축을 백분위로 바꾸면 이렇게 역전된다**는 점까지가 이 측정이 말할 수 있는
전부다. 포화를 먼저 없애지 않으면 백분위 변환만으로는 안 된다.

## 5. 따로 발견한 것 — 계약이 자정 넘는 영업시간을 표현할 수 없다

이 매장은 **09시 ~ 새벽 2시** 영업이다. 시간대별 매출 비중:

```
21시 10.6%   20시 9.3%   22시 9.7%   15시 8.6%   ...
 0시  3.9%    1시 1.9%    2시 0.4%
 3~8시 0.0~0.1% (매출 있는 날이 92일 중 2~20일)
```

`BusinessHours` 는 `opensAt`/`closesAt` 뿐이고 `_open_hours` 는 `opens <= hour < closes`
로 거른다. 09:00~03:00 을 그대로 보내면:

```
09:00~24:00 (자정에서 끊기)     남는 행 15개 · 시간대 점수  0.912
09:00~03:00 (자정 넘김)         남는 행  0개 · 시간대 점수 -1.000  ← 축 탈락
00:00~24:00 (필터 없음)         남는 행 24개 · 시간대 점수  0.999
```

`9 <= hour < 3` 은 어떤 시간에도 참이 아니라 **행이 전부 걸러지고 시간대 축이 후보에서
탈락한다** — 카드가 한 장 줄어든다. 심야 영업 매장에서 실제로 일어난다. BE 가 지금 어떤
값을 보내는지 확인이 필요하다.

## 6. 적용 — (a) 변화 금액으로 바꿨다 (2026-10-26)

`_menu_score` 를 변화율 최댓값에서 변화 금액(전체 매출 대비)으로 바꾸고, `_menu_rows` 도
같은 기준으로 정렬하게 고쳤다 — 독스트링에 적힌 대로 점수와 보여주는 행의 기준이
어긋나면 "점수를 만든 메뉴가 행에서 빠진다".

같은 POS 데이터를 **배포될 코드로** 다시 돌린 결과(표본 78일, 영업시간 09:00~24:00):

```
축          평균     표준편차   1.0 포화   선택률       (바꾸기 전)
시간대      0.983    0.012       0%      100%      100%
카테고리    0.994    0.037      96%      100%      100%
매출총액    0.324    0.199       0%       97%        0%   ← 들어왔다
메뉴        0.057    0.036       0%        3%      100%   ← 빠졌다
```

**매출총액 축이 0% → 97% 로 들어왔다.** 92일 내내 한 번도 안 나오던 축이다. 메뉴는
100% → 3% 가 됐다 — 포화가 없어지면서 "진짜로 금액이 많이 움직인 날" 에만 나온다.

부수 효과: `test_축이_다섯이면_날씨가_밀린다` 가 깨졌다. 그 테스트는 *"축이 다섯이
되면서 날씨 자리가 사실상 사라졌다, 이 테스트가 깨지면 그 결정이 내려진 것"* 이라고
적어 둔 tripwire 였다. 날씨를 건드려서가 아니라 **메뉴 포화가 날씨의 0.3 을 늘 누르고
있었기** 때문이다. 포화를 없애니 날씨 보충 자리가 돌아왔다.

**아직 안 한 것**: 시간대(평균 0.983)·카테고리(96% 포화)의 포화는 그대로다. 카드 품질
(`공허한_조언`·`수치_정확`)도 아직 재지 않았다 — `devtools/bench.py` 실행에 GPU 가 필요하다.

- **시간대·카테고리는 여전히 거의 상수다.** 시간대 표준편차 0.010~0.022(평균 0.944~0.968),
  카테고리 포화 77~91%. 즉 **카드 3장 중 2장은 아직 고정**이고, 바뀐 건 세 번째 자리가
  매출총액(85~91%)과 메뉴(9~15%) 사이에서 갈리게 된 것이다.

### §6 의 숫자를 정정한다

§6 에 적은 "메뉴 3% / 매출총액 97%" 는 **92일 한 조각의 값**이다. 639일 기준으로는
**메뉴 9~15% / 매출총액 85~91%** 다. 방향은 같지만 메뉴가 그만큼 드물게 나오지는 않는다.

### 가드 질문 — 639일 전체에서 한 번도 발동하지 않는다

"카테고리 1종이면 탈락" 류 가드가 실데이터에서 얼마나 걸리는지 같이 쟀다.

```
카테고리가 1종인 날              0 / 639
카테고리 최대 비중 >= 0.95 인 날   0 / 639
메뉴가 1종인 날                  0 / 639
```

**0건이다.** 두 매장 모두 카테고리가 13~18종이다. 2026-10-26 에 본 "미분류 100%,
2,200원" 솔루션은 테스트 매장 데이터이고, 실매장 639일에는 그런 날이 없다.

따라서 그 가드는 **일반화 성능을 올리는 변경이 아니다** — 퇴화된 입력(테스트 데이터,
POS 분류 미설정 신규 매장)에 대한 보험일 뿐이다. 넣을지는 "그런 매장이 운영에 들어오는가"
로 판단해야 하고, 이 데이터는 그 질문에 답하지 않는다.

### 그래도 남는 한계

- **매장 2곳이다.** 639 store-day 지만 매장 수는 둘이다. 매장 간 분산은 2점으로밖에
  못 본다. 매장 A 는 심야 영업(09시~새벽 2시)이라 일반적인 카페가 아닐 수 있다.
- 둘 다 **카테고리를 제대로 분류해 둔 매장**이다. 분류를 안 한 매장의 분포는 모른다.
  더 정확히는, BE 의 카테고리 매핑이 **이 매장의 POS 라벨에 하드코딩돼 있다**(§9 끝 절).
  이 데이터로는 다른 매장의 분포를 추정할 수 없다.
- 여전히 **카드 품질은 재지 않았다** — `공허한_조언`·`수치_정확` 은 GPU 가 필요하다.

## 8. 날씨 축을 기온 실측으로 바꿨다 (2026-10-26)

§7 측정에 날씨가 빠져 있었다(POS 에 기온이 없어서). 기상청 서울경기 일별 극값
(`extremum_20260908142633.xls`, 2025-01-01~2026-09-07, **615일**)을 매장 날짜에 붙여
다시 쟀다.

### 문제

`_weather_score` 가 `isNotable` 만 보고 **0.3 고정값**을 줬다. 매장 2 곳 639 일에서
매출총액 축이 평균 0.240 이라, 0.3 이 **3 번 자리를 65~69% 차지했다.**

```
평소 날씨(isNotable=true, 0.3) 켰을 때
  카드3: 날씨 69% / 매출총액 31%   (매장A)
         날씨 65% / 매출총액 35%   (매장B)
  → 메뉴 축은 0%
```

"다른 축이 할 말 없을 때만 보충" 이라고 설계했는데 반대로 동작했다. 그리고 기온 구간을
갈라 보면 그 0.3 을 받는 날의 대부분이 **음료 구성이 하루 내내 같은 평범한 날**이었다:

```
구간                                   일수   비율   아이스비중 변동폭(실험 기울기)
① 기상청 특보급 (>=33 또는 <=-12)         36    6%   —
② 하루 안에서 18℃를 가로지름             159   26%   평균 3.7%p (최대 9.8%p)
③ 하루 전부 18℃ 미만 (평범한 겨울)        254   41%   —
④ 하루 전부 18℃ 이상 (포화 구간)         166   27%   —
```

③+④ = **68%** 다. 이 날들도 똑같이 0.3 을 받았다.

### 바꾼 것

[2026-09-08 실험](2026-09-08-weather-sales.md) §1 의 두 실측값을 점수식에 직접 넣었다 —
자릿수 맞추는 임의 가중치를 쓰지 않는다.

```python
if maxTempC >= 33 or minTempC <= -12:
    return 1.0  # 기상청 주의보 기준
if not (minTempC < 18 <= maxTempC):
    return -1.0  # 구성이 안 갈린다 → 탈락
swing = (18 - max(minTempC, -10)) * 0.0061  # 1도당 아이스 비중 +0.61%p
return min(swing / 0.14, 1.0)  # 0.14 = 실험 관측 전체 변동폭
```

- **18℃** = 아이스 비중 포화점 (실험 §1)
- **0.0061** = 18℃ 미만 구간 기울기, 기온 1 도당 +0.61%p (실험 §1)
- **0.14** = 실험이 관측한 전체 변동폭 (0.338 ~ 0.478)
- **−10℃** 아래로는 기울기를 외삽하지 않는다 — 실험의 최저 구간이 (−10, 5] 다
- `isNotable` 게이트는 유지했다 — "BE 판정이 우선, 우리가 덮어쓰지 않는다"(기존 결정)

하루 최저~최고가 포화점을 가로지르는 날은 오전·오후 음료 구성이 갈려서 "오전엔 핫,
오후엔 아이스를 준비하세요" 같은 실행 가능한 말이 나온다. 가로지르지 않으면 하루 내내
같아 할 말이 없다.

### 적용 후 실측 (기상청 기온 × 매장 날짜, `isNotable=true` 가정 = **상한**)

```
매장A (309일)  날씨 발동 27% · 발동 시 평균 0.405 / 최대 1.000 · 카드 선택률 16%
  카드1: 카테고리 76% · 시간대 23% · 날씨 1%
  카드2: 시간대 73% · 카테고리 23% · 날씨 4%
  카드3: 매출총액 76% · 날씨 11% · 메뉴 8% · 시간대 4% · 카테고리 1%

매장B (253일)  날씨 발동 32% · 발동 시 평균 0.408 / 최대 1.000 · 카드 선택률 19%
  카드1: 카테고리 90% · 시간대 9% · 날씨 0%
  카드2: 시간대 85% · 카테고리 9% · 날씨 6%
  카드3: 매출총액 69% · 날씨 13% · 메뉴 11% · 시간대 6% · 카테고리 0%
```

**날씨 선택률 65~69% → 16~19%.** 평범한 날 68% 는 아예 발동하지 않는다. 특보급(한파·폭염)은
1.0 이라 그대로 1~2 번 자리를 얻는다.

### 한계

- **`isNotable=true` 를 전체 날짜에 가정한 상한이다.** 실제로 며칠이 notable 인지는 BE
  판정이라 모른다 — 그만큼 선택률은 더 낮아진다.

- 기온-아이스 비중 관계는 **매장 1 곳 267 일**에서 나온 상관이다. 인과가 아니고

- **강수는 여전히 점수에 안 들어간다.** 비 오는 날 매출 −10% 를 쟀지만(실험 §3, 42일)

  (이슈 #194). 태풍·대설은 풍속·적설이 계약에 없어 판정 못 한다 — PR #227.
- 카드 품질(`공허한_조언`·`수치_정확`)은 GPU 가 꺼져 있어 못 쟀다.

## 9. 시간대·카테고리 포화를 고쳤다 (2026-10-27)

§6~8 로 메뉴·날씨 축은 풀렸지만 **카드 1·2 는 여전히 시간대·카테고리로 고정**이었다
(§7: 시간대 표준편차 0.010~0.021, 카테고리 포화 80~90%). 그 둘을 고친 기록이다.

> **정정 (2026-10-27)**: 아래 숫자는 §7 의 측정 스크립트 버그(`drop_duplicates()` 가 같은
> 시각 같은 메뉴를 산 다른 손님을 지웠다, §7 정정 참고)를 고치고 다시 잰 값이다. 처음
> 적었던 값과 소수 둘째 자리에서 다르고, **결론은 전부 그대로다** — 어느 식을 고를지가
> 바뀌지 않았다.

### 어디서 포화가 나오는지 먼저 갈랐다

카테고리 점수는 `max(비중 최댓값, 증감률 최댓값 x 2.0)` 이다. 두 항을 따로 재봤다
(매장 2 곳, 창 7 일):

```
항                        평균(A/B)      표준편차   1.0 포화
비중 최댓값             0.421 / 0.414   0.016/0.018     0%   ← 상수. 변별이 아니라 하한이다
현행(두 항의 max)        0.955 / 0.975   0.118/0.088   80% / 88%  ← 포화는 전부 증감항
```

증감항이 원인이고, 원인은 **§3 의 꼬리 항목 문제와 같다** — 카테고리가 9~17 종이라
비중 1% 짜리 하나가 +400% 움직이면 `0.5 x 2.0` 으로 상한에 닿는다.

### 후보 네 개를 같은 데이터로 재봤다

```

현행 max(비중, 증감x2)    0.955    0.118    0.346   1.000    80%

```

### 카테고리에 메뉴와 같은 잣대를 쓰면 안 된다

§6 에서 메뉴를 "변화 금액" 으로 바꿨으니 카테고리도 같게 하는 게 자연스러워 보인다.
**아니다.** 카테고리의 변화 금액은 그 카테고리에 속한 메뉴들의 변화 금액 **합**이라
개별 메뉴 최댓값보다 구조적으로 크다. 실제로 그렇게 하면 메뉴 축이 다시 밀린다:

```
카드3 구성          카테고리=TVD        카테고리=변화금액x2
매장A   메뉴            39%                  16%
매장B   메뉴            32%                  13%
```

`_menu_score` 독스트링의 *"메뉴 비중은 카테고리보다 구조적으로 작다 — 같은 잣대로 재면
메뉴 축이 거의 항상 진다"* 와 **반대 방향인 같은 함정**이다. 그래서 잣대를 가른다:
메뉴는 "한 메뉴가 크게 움직였다"(변화 금액 최댓값), 카테고리는 "구성이 재편됐다"(총변동).

### 바꾼 것

```python
# 시간대 — 균등하게 팔렸다면 영업시간 n 개가 1/n 씩 가져간다. 모자란 몫의 합.
#          dayType 별로 따로 재서 더 쏠린 쪽을 쓴다(평일·주말은 다른 계열이다).
even = 1.0 / len(amounts)
score = sum(max(0.0, even - a / total) for a in amounts)

# 카테고리 — 비중의 총변동거리. share 와 vsPrevPeriod 로 이전 비중이 복원된다.
prev_i = share_i / (1 + vsPrevPeriod_i)          # 합으로 나눠 비중으로 되돌린다
score  = 0.5 * sum(|share_i - prev_i_정규화|)
```

둘 다 **자릿수 맞추는 가중치가 없다.** 0~1 범위가 식 자체에서 보장되고, 메뉴·매출총액과
같은 단위(전체 매출 또는 비중의 몇 %)가 된다. 비중 쏠림 항은 뺐다 — "커피가 62%" 는
늘 그래서 뉴스가 아니다(`_menu_score` 의 "늘 아메리카노가 1 위다" 와 같은 판단).

`_category_rows` 도 같이 바꿨다. 점수 기준이 구성 변동으로 바뀌었는데 행은 비중 상위로
고르고 있어서, **가장 많이 움직인 카테고리가 행에 없는 날이 17~23%** 였다(매장A 61/351,
매장B 58/253). §6 에서 `_menu_rows` 로 먼저 겪은 문제다.

시간대 표준편차가 0.016 → 0.031 으로 두 배가 됐지만 여전히 작고, 선택률은 639 일 전부
100% 다 — 슬롯은 안 고정됐지만 축 자체는 늘 든다.

**이건 점수식으로 풀 수 있는 문제가 아니다.** `HourlyPoint` 는 `dayType`·`hour`·`amount`
뿐이라 비교 대상이 없다. 매출총액 축이 표준편차 0.182 인 건 그 축만 두 기간의
비(`vsPrevPeriod`)이기 때문이다.

이번 변경이 고친 것은 변별력이 아니라 **다른 축을 덮던 높이**다(0.96 → 0.255).

#### 정정 (2026-10-27) — "날짜별" 이라는 틀이 애초에 틀렸다

이 절을 처음 쓸 때 *"7 일 창이 하루씩 미끄러지면 6/7 이 겹쳐서 모양이 안 변한다"* 고
적었다. **운영에서 창이 하루씩 미끄러지지 않는다.** BE(`KTB4-7th-BE`)를 확인한 결과다.

```java
// SalesSolutionMetricsAssembler.assemble()
LocalDate start = analysisRun.getPeriodStart();
LocalDate end = analysisRun.getPeriodEnd().isBefore(forecast.getTargetDate())
        ? analysisRun.getPeriodEnd()
        : forecast.getTargetDate().minusDays(1);
long days = ChronoUnit.DAYS.between(start, end) + 1;
LocalDate previousEnd = start.minusDays(1);
LocalDate previousStart = previousEnd.minusDays(days - 1);
```

- **창 길이가 7 일 고정이 아니다.** 분석 기간과 같은 길이의 바로 앞 구간이고, 분석 기간은
  업로드한 POS 파일의 날짜 범위다(`SalesUploadPersistenceService` → `workbookData`).
  3 개월 파일이면 창이 90 일이다.
- **업로드 사이에는 지표가 전혀 안 변한다.** `SalesSolutionGenerationContextResolver.resolve`
  가 `latestCompletedRun(storeId)` 을 쓰므로 SCHEDULED(매일 00:00 배치)도 같은
  `analysisRun` 을 다시 쓴다. 업로드 데이터는 항상 오늘보다 전에 끝나니 `end = periodEnd`
  로 고정된다. 다음 업로드까지 시간대·카테고리·메뉴·매출총액 점수가 **매일 동일하다.**
  날마다 바뀌는 입력은 `predictedSalesToday` 와 `weatherContext` 둘뿐이다.

그래서 "날짜별 변별력" 은 못 푼 과제가 아니라 **성립하지 않는 개념**이다. 축이 재야 하는
단위는 날짜가 아니라 **매장·업로드**다.

**§1~9 의 측정과 결론은 그대로 유효하다.** 고친 대상은 포화(= 한 축이 다른 축을 덮어
카드 1·2 가 고정되는 것)였고, 그건 창이 어떻게 움직이든 모든 입력에서 성립한다.

다만 **표준편차 숫자의 해석을 바꿔야 한다.** 639 store-day 는 겹치는 창이라 독립 표본이
아니고 운영의 "하루하루" 도 아니다. `시간대 표준편차 0.017` 은 *"창을 옮겨도 점수가 안
변한다"* 로 읽어야 하고, *"매일 같은 점수가 나온다"* 의 근거로는 쓸 수 없다 — 후자는 창
구조상 당연해서 측정할 필요가 없던 사실이다.

#### 그래서 `hourlyProfile.vsPrevPeriod` 요청은 보류한다

이전 기간 값을 받는 것 자체는 여전히 할 만하다. 현행이 재는 "피크가 있나" 는 카페에서
늘 참이라 "9 시가 다른 시간대보다 낮습니다" 가 뉴스가 아니고, 받으면 "어느 시간대가
꺾였나" 를 잴 수 있다. BE 변경도 작다 — `assemble()` 이 `previous` 를 이미 로드해
`categoryBreakdown` 에만 넘기고 있어서 `hourlyProfile(current, previous)` 로 바꾸고 기존
`changeRate()` 헬퍼를 재사용하면 된다. **쿼리 추가가 없다.**

POS 로 `vsPrevPeriod` 를 만들어 후보 네 개를 재봤다(매장 2 곳).

```
창 7일 · 매장A           평균     표준편차   1.0포화   시간대 선택률
현행 유휴비중(비교 안 씀)  0.255    0.031      0%       100%
(a) 증감률 최댓값        0.976    0.074     87%       100%  ← 카드1 을 100% 차지
(b) 변화금액 최댓값       0.034    0.010      0%        33%
(c) 구성 TVD            0.159    0.029      0%        99%
(d) 하락분 합            0.089    0.041      0%        83%

창 7일 · 매장B (253일) — 같은 방향
(a) 0.971 포화 84% 선택률 100% · (b) 0.033 선택률 25% · (c) 0.161 선택률 99%
(d) 0.095 선택률 77%
```

**(a) 는 현행보다 나쁘다.** 받은 `vsPrevPeriod` 를 그대로 쓰면 84~87% 포화되고 카드 1 을
100% 차지한다 — 아침 9 시가 8 천원 → 3 만원이면 +275% 인데 금액은 전체의 0.1% 다.
메뉴(§6)·카테고리(§9)에서 고친 꼬리 항목 문제가 **세 번째로 똑같이** 재현된다.

(d) 하락분 합(`꺾인 시간대들의 손실 금액 / 전체 매출`)이 가장 낫다. 축이 실제로 탈락하고
(선택률 83%/77%), 슬롯이 고르게 퍼지고, 하락만 보는 비대칭이 솔루션 축에 맞다 — 늘어난
것은 매출총액 축이 말한다.

**그런데 창 길이에 의존한다.** 위에서 확인한 대로 창은 업로드 파일 범위라 7 일이 아니다.

```
창      (d) 평균 ± 표준편차 (A / B)        매출총액 상관 (A / B)
 7일    0.089±0.041 / 0.095±0.053         -0.12 / +0.29
30일    0.065±0.035 / 0.068±0.039         -0.01 / +0.01   ← 가장 깨끗하다
90일    0.052±0.042 / 0.038±0.030         **+0.50** / -0.03
```

30 일 창이 가장 깨끗하다(매출총액과 거의 무상관). **90 일 창에서는 매장A 가 매출총액 축과
0.50 상관**이라 같은 말을 하는 카드가 두 장 나갈 수 있다.

**점주들이 실제로 올리는 파일의 기간 분포를 알아야 요청의 근거가 선다.** 그런데 그건
**우리가 알 방법이 없다** — 운영 중인 서비스가 아니고, 가진 파일 두 묶음도 알바하는 분이
사장님께 직접 여쭤서 받아온 것이다. BE 에 쌓인 `analysis_runs` 도 팀 테스트 업로드뿐이다.

따라서 이 요청은 **데이터로 닫을 수 없다.** 창 길이를 모르는 상태로 보류하거나, 창 길이에
무관한 형태(예: 창 길이를 점수식에 반영)를 따로 설계해야 한다. 지금은 보류한다.

계약 모양 걱정은 접었다. "이전 기간엔 있었는데 이번엔 사라진 시간대" 를 현재 기간 행에만
`vsPrevPeriod` 를 붙이는 모양으로는 담을 수 없는데, 영업시간 안쪽에서 재면 0.01~0.03 행/일
이고 **최대 하락 시간대가 사라진 행인 날은 639 일 중 0 일**이었다. `prevAmount` 같은 걸
따로 요청할 필요가 없다.

#### 같이 확인된 것 — 카테고리 분류 체계가 둘이다

솔루션의 `categoryBreakdown` 은 메뉴판 등록의 6 종(`COFFEE/TEA/BEVERAGE/CAKE/BAKERY/OTHER`)이
아니라 BE 의 `SalesStandardMenuCategory` **12 종**을 쓴다.

```
COFFEE · NON_COFFEE · TEA · ADE · SMOOTHIE · BOTTLED_DRINK
BEER · CAKE · BAKERY · FOOD · SEASONAL · UNMAPPED
```

`NON_COFFEE` 가 BE 쪽에 아직 있다 — AI 계약에서는 2026-10-14 에 `TEA` 로 바꿨다. `ADE`·
`SMOOTHIE` 가 AI 쪽 `BEVERAGE` 하나에 뭉쳐 있다. 이 절에서 바꾼 `_category_score` 가 재는
건 이 12 종이고, 측정에 쓴 POS 원본 카테고리(9~17 종)와도 또 다르다.

**그리고 그 매핑이 한 매장의 POS 라벨에 하드코딩돼 있다.**
`TossPosWorkbookParser.standardCategory()`:

```java
case "esp" -> COFFEE;          case "non" -> NON_COFFEE;
case "teabag" -> TEA;          case "ade" -> ADE;
case "smoothie" -> SMOOTHIE;   case "beverage" -> BOTTLED_DRINK;
case "beer" -> BEER;           case "cake" -> CAKE;
case "bakery" -> BAKERY;       case "food", "snack" -> FOOD;
case "루미코르 팝업", "신메뉴 라인업", "신메뉴 우베라인업" -> SEASONAL;
default -> UNMAPPED;
```

`TossPosTextNormalizer.category()` 는 공백 정리 + 소문자화 후 **정확히 일치**만 본다 —
접두어도 유사 매칭도 없다. `"커피"`·`"에스프레소"`·`"디저트"` 는 물론이고 **`"coffee"` 조차
UNMAPPED** 다(키가 `"esp"` 이므로). `"루미코르 팝업"` 은 특정 카페의 시즌 메뉴 이름이다.

우리 데이터로 돌려보면 매핑률이 **매장A 97.6% · 매장B 95.4%** 로 높다. 그런데 이건 잘
되는 게 아니라 **순환이다** — BE 가 이 매장의 POS 라벨을 보고 하드코딩했으니 이 매장에선
당연히 맞는다. 그리고 §7 정정대로 두 묶음은 같은 브랜드다.

**2026-10-26 에 본 "전체 매출의 100%가 미분류 카테고리에 집중되어 있어" 솔루션은 테스트
데이터 문제가 아니다.** POS 라벨이 다른 모든 매장에서 그렇게 된다. BE 레포에 이슈로 올렸다.

## 10. 제나 리뷰 두 건을 재보고, 하나를 고쳤다 (2026-10-27)

#243 리뷰에서 제나가 두 가지를 짚었다. 둘 다 실재했고, 하나는 우리 쪽에서 닫을 수 있고
하나는 BE 계약이 막고 있다.

### 10-1. 유휴 비중의 분모가 틀렸다 → 고쳤다

`_hourly_score` 가 `1/len(amounts)` 를 균등 몫으로 썼다. `amounts` 는 `_selling` 이 0 원
행을 걸러낸 뒤의 행들이라, **영업 중인데 한 잔도 안 팔린 시간이 분모에서 같이 사라진다.**
가장 유휴인 시간이 점수에 반영되지 않아 쏠림을 과소평가한다.

분모를 `businessHours` 의 영업시간 수로 바꿨다. 빠진 시간의 몫 `1/n` 은 통째로 비어 있는
매출이라 그대로 더한다. 영업시간이 없거나(BE 미전송) 행 수가 영업시간 수보다 많으면
행 수로 떨어진다.

| 분모 | 매장A 평균 | 매장B 평균 | 포화 |
|---|---|---|---|
| 현행 — 매출 있는 행 수 | 0.255 (σ 0.031) | 0.254 (σ 0.034) | 0% |
| 영업시간 수 (선언창 정확) | **0.255** (σ 0.032) | **0.254** (σ 0.034) | 0% |
| 영업시간 수 (선언창 +2h) | 0.312 | 0.311 | 0% |
| 영업시간 수 (선언창 +4h) | 0.364 | 0.364 | 0% |

**우리 데이터로는 아무것도 바뀌지 않는다** — 두 매장 모두 영업시간 내 모든 시간에 매출이
있다. 바뀌는 건 한가한 매장이고, 거기서는 지금 식이 100% 틀린다.

포화 위험을 같이 봤다. BE 의 `businessHours` 는 `StoreBusinessHours`(점주 등록)에서 오므로
실제보다 넓을 수 있다. 선언창을 +4 시간 부풀려도 평균 0.364 · 최대 0.426 · 포화 0% 로
다른 축이 이길 자리가 남는다. 안전하다고 본다.

### 10-2. 자정을 넘긴 영업시간은 축을 통째로 날린다 → 같이 고쳤다

BE 의 `businessHours` 는 `schedule.getOpensAt()`·`getClosesAt()` 을 **순서 검사 없이 그대로**
내보낸다. 그래서 11:00~02:00 매장이 그 값 그대로 온다. `_open_hours` 의
`opens <= hour < closes` 는 11~2 사이에서 한 번도 참이 되지 않아 **시간대 행이 전부
걸러지고 축이 후보에서 빠진다.** 닫는 시가 여는 시보다 작거나 같으면 24 를 더하도록 했다
(24 시간 영업 `00:00~00:00` 도 같은 경로로 0~24 가 된다).

우리 POS 두 매장은 09:00~24:00 으로 유도돼 이 경로를 타지 않는다. 코드 경로상의 결함이라
실측 근거는 없고, 테스트로 고정했다.

### 10-3. 메뉴·카테고리의 `vsPrevPeriod` 처리 → BE 계약이 막고 있다

`_menu_share_delta` 와 `_category_share_shift` 의 주석이 **틀린 주장을 담고 있었다**:
"그 메뉴는 현재 매출이 0 이라 랭킹에 올 수 없다". BE 코드를 읽으면 반대다.

`menuRankings` 는 랭킹을 현재·이전 **합집합**으로 만들고(`allMenuTotals`), 변화율 큰 순으로
다섯 종을 더 끼워 넣는다. 사라진 메뉴의 변화율은 -1.0 이라 `abs` 가 **가능한 최댓값**이어서
BE 가 1 순위로 올려 보내는 행이다. 그런데 그 행은 `ratio` 가 0 이라 우리 등식으로 크기를
복원할 수 없고, 우리는 0.0 으로 버린다.

`categoryBreakdown` 은 반대로 **현재 기간만** 훑어서(`currentTotals.entrySet()`) 이전에만
있던 카테고리가 목록에 아예 없다.

BE 선정 로직(`MAX_MENU_RANKING_GROUP_SIZE=5`, `MIN_BASELINE_AVERAGE_DAILY_QUANTITY=3`)을
그대로 재현해 604 창(창 7 일)을 재봤다.

| | 발생 창 | 버리는 비중 (중앙) | (최대) |
|---|---|---|---|
| 메뉴 `vsPrevPeriod == -1.0` | 54 / 604 (9%) | 0.01~0.70% | 3.35% |
| 카테고리가 목록에서 누락 | 164 / 604 (22~31%) | 0.34~0.69% | 4.41% |

메뉴 쪽 영향을 더 쪼개면:

- 축 **점수**가 올라가는 창: 54 중 1 (+0.0062). 거의 안 움직인다.
- 제대로 세면 **표시 5 행에 드는 창: 54 중 12.** 현행은 델타 0.0 이라 맨 뒤로 밀려 전부
  잘린다 — **BE 가 일부러 올려 보낸 행을 우리가 매번 버린다.**

점수보다 표시 행이 문제다. 그리고 `previousRatio`(또는 `previousMenuSales`) 없이는 크기를
낼 방법이 없다. 카테고리도 합집합과 `previousShare` 가 있으면 복원 수식 자체가 불필요해진다.
BE 에 요청했다(BE #623).

  하루 0.01~0.03 행이라 바뀔 여지가 없다. +2h/+4h 부풀림은 점주 선언 오차의 **시뮬레이션**
  이고, 실제 선언창과 실제 영업의 차이는 관측한 적이 없다.
- 10-2 는 실측이 아니라 코드 경로 분석이다.
- 10-3 의 숫자는 창 7 일 기준이다. 실제 BE 비교 기간은 업로드 파일의 날짜 범위라
  `MIN_BASELINE_AVERAGE_DAILY_QUANTITY x 기간` 문턱이 훨씬 높아지고, 꼬리 메뉴가 더
  걸러진다 — 발생률은 9% 보다 **낮을** 가능성이 있다.
